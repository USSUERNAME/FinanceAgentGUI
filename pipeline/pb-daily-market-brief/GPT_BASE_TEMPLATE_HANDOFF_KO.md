# PB 데일리 마켓 리포트 베이스 템플릿 인수인계서

이 문서는 이 저장소의 **리포트 디자인, 정보 구조, 안전장치와 기본 코드 구조**를 다른 사람의 GPT/Codex가 그대로 이해하고 유지·확장하도록 전달하기 위한 문서다.

API 키 등록, GitHub Actions 실제 발행, 새로운 자료의 등록 방법은 리포트 운영자가 별도로 교육한다. 상대 GPT는 이 문서를 읽고 그 영역을 임의로 변경하거나 대신 설명하려 하지 않는다.

## 1. 인수인계 범위

### 이 문서로 넘기는 것

- Notion 리포트의 시각적 위계와 카드 디자인
- 독자용 리포트의 고정 목차와 작성 규칙
- 데이터 수집, 분석, 작성, 렌더링의 역할 분리
- 사실·해석·확인 조건·무효화 조건의 구분
- 뉴스·공시의 출처 등급과 품질 게이트
- 미국 시장·섹터·개별주 분석의 기본 배치
- 독자용 리포트와 내부 운영 보고서의 분리
- 리포트 완성 여부를 판정하는 검증 기준
- 디자인을 변경할 때 지켜야 할 회귀 테스트

### 운영자가 직접 교육할 것

- API 키와 토큰 등록
- GitHub Secrets 설정
- GitHub Actions 실행과 실제 발행
- Notion·Telegram 계정 연결
- 새로운 기사, 리서치 자료, 공시 소스의 등록
- 유료 자료의 이용 권한과 수동 자료 투입 방법

### 상대 GPT가 하지 말아야 할 것

- 채팅으로 API 키나 토큰을 요청하거나 출력하기
- `.env` 또는 Secret 값을 코드·문서·로그에 기록하기
- 운영자의 허락 없이 실제 발행하기
- 유료 리서치 원문을 복제하거나 무단 크롤링하기
- 검증되지 않은 뉴스나 공시 제목을 확인된 사실로 바꾸기
- 숫자, 컨센서스, 발표일, 인용문을 추측해 채우기
- 매수·매도, 목표주가 또는 확정적 전망을 만들기

## 2. 상대 GPT에게 처음 전달할 프롬프트

아래 블록을 새 GPT/Codex 작업의 첫 메시지로 그대로 전달한다.

```text
이 저장소는 증권 PB용 한국어 데일리 마켓 리포트 템플릿이다.

작업을 시작하기 전에 다음 파일을 순서대로 모두 읽어라.

1. GPT_BASE_TEMPLATE_HANDOFF_KO.md
2. handoff/REPORT_DESIGN.md
3. handoff/DATA_CONTRACT.md
4. compose_daily_brief.py
5. publish_to_notion.py
6. publish_visual_brief.py
7. run_daily_report.py
8. .github/workflows/daily-brief.yml

이번 인수인계 범위는 템플릿 디자인, 정보 구조, 분석/렌더링 분리,
품질 게이트와 검증 기준이다.

API 키 등록, GitHub Secrets, 실제 발행, 새 자료 등록 방법은 운영자가
직접 교육한다. 해당 설정을 임의로 바꾸거나 비밀값을 요청하지 마라.

코드를 수정하기 전에 먼저 아래 내용을 짧게 보고하라.

- 현재 리포트 생성 흐름
- 디자인을 결정하는 파일
- 고정해야 할 목차와 시각 규칙
- 요청한 변경이 영향을 주는 파일
- 사실성, 모바일 가독성, 리포트 완결성을 검증할 테스트

그 후 운영자의 승인을 받은 범위만 수정하라.

항상 지킬 규칙:

- 데이터 수집, 계산, AI 해석, Markdown 구성, Notion 렌더링을 분리한다.
- 제공된 데이터 밖의 숫자와 사실을 생성하지 않는다.
- 사실, 해석, 확인 조건, 무효화 조건을 구분한다.
- 출처 URL, 관측일, 출처 등급, 검증 상태를 보존한다.
- source_grade D 또는 metadata_only 자료는 확인된 사실로 쓰지 않는다.
- 독자용 본문에 내부 변수명, 빈 운영 큐, SLA 로그를 노출하지 않는다.
- 핵심 시장 결론은 단순 risk-on/off보다 실제 자산 로테이션을 우선한다.
- 빈 섹션은 짧게 숨기거나 축약하며 일반론으로 채우지 않는다.
- 리포트 마지막의 <!-- REPORT_COMPLETE --> 표식을 유지한다.
- 실제 발행은 운영자의 명시적 요청이 있을 때만 한다.
```

## 3. 시스템의 역할 분리

이 저장소의 기본 흐름은 다음과 같다.

```text
공식 API·허용된 피드·운영자 자료
        ↓
수집 및 정규화
        ↓
규칙 기반 계산·중복 제거·품질 등급
        ↓
시장·섹터·개별주 구조화 분석
        ↓
독자용 Markdown 구성
        ↓
차트 생성
        ↓
Notion 네이티브 블록 렌더링
        ↓
발행 결과·이력·근거 보존
```

핵심 파일의 책임은 다음과 같다.

| 파일 | 책임 | 디자인 변경 시 원칙 |
|---|---|---|
| `run_daily_report.py` | 전체 단계의 실행 순서 | 디자인 문구를 이곳에 넣지 않는다 |
| `build_daily_snapshot.py` | 시장 데이터를 하나의 일일 스냅샷으로 결합 | 표시용 문장보다 구조화 필드를 만든다 |
| `analyze_market_snapshot.py` | 시장 체제, 핵심 동인, 충돌 신호 판단 | 렌더링을 담당하지 않는다 |
| `compose_daily_brief.py` | 고정 목차에 맞춘 독자용 Markdown 구성 | 제공된 근거만 사용하고 완결성을 검사한다 |
| `publish_to_notion.py` | Markdown을 Notion 블록·카드로 변환 | 색상, 열 수, 아이콘, 빈 상태 표현을 관리한다 |
| `publish_visual_brief.py` | 차트와 본문을 올바른 위치에 삽입 | 분석 내용을 다시 쓰지 않는다 |
| `generate_market_pulse.py` | 상단 시장 펄스 이미지 | 상단 결론을 보조하고 본문을 대체하지 않는다 |
| `generate_macro_chart.py` | 거시 차트 | 관측일과 최신값을 정확히 보존한다 |
| `generate_etf_chart.py` | ETF 추세·상대강도 차트 | 표시 단위와 기간을 일관되게 유지한다 |
| `.github/workflows/daily-brief.yml` | 자동 실행과 운영 모드 | 운영자가 교육하는 영역으로 임의 변경 금지 |

분석 로직을 `publish_*` 파일에 넣거나, Notion 디자인 코드를 수집기에 넣으면 안 된다. 같은 분석 결과를 Markdown, Notion, Telegram 등 여러 출력에서 일관되게 재사용하기 위해서다.

## 4. 고정 디자인 계약

### 4.1 전체 인상

리포트는 화려한 뉴스 사이트가 아니라 **기관형 데일리 브리프**처럼 보여야 한다.

- 흰 배경 위에 Notion 기본 블록을 사용한다.
- 파랑은 결론·거시, 초록은 시장 지표·ETF, 노랑은 뉴스·핵심 변수, 보라색은 공시, 빨강은 위험과 중요 종목에 사용한다.
- 긴 문단보다 제목, 한 줄 결론, 카드, 짧은 근거 순서로 읽히게 한다.
- 데스크톱과 모바일 모두에서 읽을 수 있도록 폭이 좁은 다열 카드를 피한다.
- 색만으로 의미를 전달하지 않고 아이콘, 제목, 텍스트를 함께 사용한다.

### 4.2 페이지 상단

상단은 두 개의 카드로 구성한다.

```text
┌──────────────────────────┬──────────────────────┐
│ PB RESEARCH              │ AS OF                │
│ DAILY MARKET INTELLIGENCE│ YYYY-MM-DD           │
│ YYYY-MM-DD 리포트        │ INTERNAL MONITORING  │
└──────────────────────────┴──────────────────────┘
```

- 왼쪽: 파란 배경, 신문 아이콘, 리포트 브랜드와 전체 날짜
- 오른쪽: 노란 배경, 달력 아이콘, 기준일과 내부 모니터링 표시
- Notion의 실제 페이지 제목은 모바일 줄바꿈을 줄이기 위해 `MM.DD 리포트`로 짧게 표시한다.
- 상단 카드 다음에는 Notion 목차 블록을 둔다.

구현 위치:

- `publish_to_notion.py::report_masthead`
- `publish_to_notion.py::compact_page_title`
- `publish_to_notion.py::report_navigation`

### 4.3 오늘의 결론

첫 화면에서 반드시 아래 네 항목이 순서대로 보여야 한다.

1. `시장 체제`
2. `오늘의 결론`
3. `핵심 변수`
4. `최우선 리스크`

Notion에서는 다음처럼 렌더링한다.

- 전체 폭의 파란색 `오늘의 결론` 카드
- 그 아래 3열 카드:
  - 시장 체제: 회색
  - 핵심 변수: 노란색
  - 최우선 리스크: 빨간색
- 카드 아래에 시장 펄스 차트
- 이어서 최대 3개의 핵심 동인을 아래 구조로 작성

```text
관측 → 해석 → 확인 조건 → 무효화 조건
```

시장 체제는 단순히 `risk-on` 또는 `risk-off`만 사용하지 않는다. 필요하면 `선별적 순환매`, `혼합`, `방어적 로테이션`처럼 리더와 부진 자산의 조합을 설명한다.

### 4.4 시장 스코어보드

시장 스코어보드는 데스크톱에서 세로로 길어지거나 카드가 지나치게 좁아지지 않도록 **한 행에 2개 카드**를 기본으로 한다.

- 시장 폭
- 변동성
- 크레딧
- 금리

마지막 `모니터링 신호`는 별도의 전체 폭 회색 카드로 둔다.

4열 카드는 직접적인 지표명과 설명이 잘리므로 사용하지 않는다. 지표가 홀수 개라면 마지막 하나는 전체 폭 카드로 표시한다.

구현 위치:

- `publish_to_notion.py::scoreboard_blocks`
- `compose_daily_brief.py::deterministic_scoreboard_section`

### 4.5 차트 위치

차트는 아래 제목 바로 다음에 자동 삽입한다.

| 섹션 | 차트 |
|---|---|
| 오늘의 결론 | 시장 펄스 |
| 거시 지표와 시장 맥락 | 미국 거시 모니터링 |
| ETF 모니터링 | ETF 가격 추세, ETF 상대강도 |
| 해외 뉴스 | 모바일용 한국어 뉴스 카드, 있을 때만 |

차트 안의 숫자는 구조화 데이터에서 생성하며, Notion의 만료되는 이미지 URL이나 외부 기사 이미지를 입력으로 사용하지 않는다.

구현 위치:

- `publish_visual_brief.py::chart_after_heading`

### 4.6 뉴스·공시·종목 카드

- 해외 뉴스 제목: 노란색 카드, 신문 아이콘
- 국내 공시 제목: 보라색 카드, 문서 아이콘
- 종목·SEC 공시 제목: 빨간색 카드, 파일 아이콘
- 항목이 없을 때: 회색 카드 또는 한 줄 빈 상태

뉴스 카드의 기본 본문:

```text
출처 등급
1차 자료 확인
제한된 요약
중요한 이유
원문 링크
```

개별주 카드의 기본 본문:

```text
선정 이유
확인된 사실
가격·거래량 반응
시장·섹터 대비 반응
섹터 전이 가설
확인 조건
무효화 조건
근거 등급과 URL
```

## 5. 독자용 고정 목차

`compose_daily_brief.py`가 검사하는 기본 순서는 아래와 같다.

1. 오늘의 결론
2. 데이터 기준과 수집 상태
3. 시장 스코어보드
4. 전일 가설 점검
5. 향후 이벤트 시나리오
6. 가설 누적 성과
7. 거시 지표와 시장 맥락
8. ETF 모니터링
9. 해외 뉴스
10. 국내 공시
11. 종목 및 공시
12. 다음 확인 항목
13. 출처 및 유의사항

미국 개별주 분석은 `종목 및 공시` 안에 결정론적으로 삽입한다. 섹터 가설 변화와 섹터 리더십 퍼널은 `ETF 모니터링`에서 시장 리더십과 연결한다.

목차를 바꿀 때는 다음 세 곳을 함께 검토한다.

- `compose_daily_brief.py::REQUIRED_HEADINGS`
- `compose_daily_brief.py`의 모델 지시문
- `publish_to_notion.py::SECTION_COLORS`와 `SECTION_CARD_STYLES`

목차 이름만 바꾸고 렌더러 매핑을 수정하지 않으면 차트와 카드가 잘못된 위치에 들어간다.

## 6. 독자용 본문과 내부 운영 자료 분리

독자용 리포트에는 아래 항목을 기본적으로 노출하지 않는다.

- 수집기 디버그 로그
- 원시 JSON 변수명
- 빈 승인 큐
- 빈 SLA·담당자 큐
- 외부 근거 백로그
- 내부 해시와 운영 상태 코드
- `wait_for_proof`, `not_research_ready` 같은 원시 상태값

필요한 경우 사람이 읽는 한국어로 번역하고, 의사결정에 필요한 결과만 표시한다.

내부 운영 자료는 별도 파일에 보존한다.

```text
workspace/operations_reports/YYYY-MM-DD_operations.md
```

원칙은 다음 한 문장으로 요약한다.

> 내부 시스템은 복잡하게 유지하되, PB가 읽는 화면은 짧고 분명하게 만든다.

## 7. 사실성과 품질 게이트

### 7.1 출처 등급

- A: 기업 IR, SEC, OpenDART, 중앙은행, 정부기관 등 1차 자료
- B: 복수의 신뢰도 높은 주요 매체로 확인
- C: 단일 주요 매체
- D: 메타데이터, 재전송 기사, 본문 미확보 자료

`source_grade: D` 또는 `evidence_scope: metadata_only`는 기사·공시의 존재를 알려주는 검토 후보일 뿐이다. 리포트의 핵심 사실이나 확정적 해석 근거로 사용하지 않는다.

### 7.2 사실과 해석

각 판단은 가능한 한 아래 형태를 따른다.

```text
[확인된 사실]
원문과 수치로 직접 확인된 내용

[해석]
사실에서 파생한 제한된 시장 가설

[확인 조건]
가설이 맞는 방향으로 진행되는지 볼 지표

[무효화 조건]
가설을 폐기하거나 다시 검토할 직접 조건
```

원인 지표와 결과 지표를 구분한다. 예를 들어 실질금리 상승 가설의 확인 조건은 실질금리 자체뿐 아니라 QQQ/SPY 또는 SOXX/SPY 같은 결과 지표를 함께 사용한다.

### 7.3 데이터 날짜

아래 날짜를 혼용하지 않는다.

- 리포트 날짜
- 가격 기준일
- 관측일
- 발표일
- 수집 시각

월간 거시지표의 관측월을 발표일처럼 쓰면 안 된다. 가격 기준일이 리포트 날짜보다 이전이면 주말, 휴일 또는 공급자 시차 가능성을 명시한다.

### 7.4 숫자 표시

- 수익률·상대수익률: 소수점 둘째 자리
- 금리 수준: 소수점 둘째 자리
- 금리 변화: bp
- 비율: 소수점 둘째 자리
- 점수: 정수 또는 꼭 필요한 한 자리
- 내부 계산의 긴 부동소수점은 독자 화면에서 숨김

## 8. 빈 상태 처리

데이터가 없을 때 일반적인 시장 해설로 채우지 않는다.

좋은 예:

```text
중요 국내 공시 없음(수집 범위 기준).
컨센서스 자료 없음.
상대강도 계산 자료 없음.
판정 완료 표본이 10건 미만이어서 적중률을 표시하지 않습니다.
```

나쁜 예:

```text
시장은 다양한 변수에 따라 움직일 수 있으므로 주의가 필요합니다.
```

빈 항목이 많은 섹션은 한 줄로 축약하거나 숨긴다. 운영상 필요한 상세 실패 정보는 내부 운영 보고서에 남긴다.

## 9. 디자인 변경 절차

상대 GPT는 디자인 요청을 받으면 아래 순서로 작업한다.

1. 요청이 정보 구조, Markdown 구성, Notion 렌더링, 차트 중 어디에 해당하는지 분류한다.
2. 현재 파일을 읽고 기존 사용자 변경과 겹치는지 확인한다.
3. 영향을 받는 파일과 예상 화면 변화를 먼저 설명한다.
4. 최소 범위로 수정한다.
5. 샘플 또는 기존 아티팩트로 Markdown을 생성한다.
6. Notion 호출 없이 시각 렌더링 드라이런을 통과시킨다.
7. 관련 테스트와 전체 테스트를 실행한다.
8. 실제 발행은 운영자의 명시적 요청이 있을 때만 한다.

새로운 디자인 기능을 넣을 때는 반드시 아래 질문에 답해야 한다.

- 데스크톱에서 한눈에 읽히는가?
- 모바일에서 열이 무너지거나 글자가 작아지지 않는가?
- 같은 내용이 이미지와 본문에 중복되지 않는가?
- 색이 없어도 의미가 전달되는가?
- 원문 링크와 데이터 날짜가 남아 있는가?
- 빈 상태가 과도한 공간을 차지하지 않는가?
- 내부 운영 상태가 독자 화면으로 새지 않는가?

## 10. 검증 기준

### 필수 구조 검증

- 제목이 `# YYYY-MM-DD 리포트` 형식이다.
- 필수 13개 섹션이 지정 순서로 존재한다.
- 필수 섹션이 비어 있지 않다.
- 문서 마지막에 아래 표식이 존재한다.

```html
<!-- REPORT_COMPLETE -->
```

- 출처 섹션은 실제 수집 URL에서 결정론적으로 생성된다.
- 원시 내부 변수명과 긴 소수점이 독자 화면에 노출되지 않는다.
- 운영 보고서는 독자용 본문과 별도 파일이다.

### 시각 검증

- 상단 두 카드와 목차가 생성된다.
- 오늘의 결론이 전체 폭 카드와 3개의 신호 카드로 보인다.
- 시장 스코어보드는 한 행 2개 카드다.
- 시장 펄스, 거시, ETF 차트가 올바른 제목 뒤에 삽입된다.
- 뉴스·공시·종목 카드의 색과 아이콘이 역할에 맞는다.
- 100개가 넘는 Notion 하위 블록도 분할 업로드된다.

### 안전성 검증

- Grade D와 metadata-only 자료가 확인된 사실로 승격되지 않는다.
- 컨센서스나 발표일이 없으면 `자료 없음`으로 표시된다.
- 기사 원문을 길게 복제하지 않는다.
- 비밀값이 결과물·로그·커밋에 없다.
- 매수·매도·목표주가가 생성되지 않는다.

### 관련 테스트

최소한 아래 테스트를 실행한다.

```powershell
python -m pytest tests/test_publish_visual_brief_dry_run.py
python -m pytest tests/test_cached_brief_publish.py
python -m pytest tests/test_us_market_internals.py
python -m pytest tests/test_us_equity_candidate_screen.py
python -m pytest
```

프로젝트에서 사용하는 Python 실행 방식이 다르면 동일한 환경의 명령으로 바꾸되, 테스트 범위를 줄이지 않는다.

## 11. 완료 보고 형식

상대 GPT는 작업 완료 후 아래 형식으로 보고한다.

```text
완료한 변경
- 독자 화면에서 바뀐 점
- 변경한 파일

보존한 계약
- 목차 순서
- 출처·사실성 게이트
- REPORT_COMPLETE
- 독자용/운영용 분리

검증
- 실행한 테스트와 결과
- 드라이런 블록 수와 이미지 수
- 모바일·데스크톱 가독성 확인 결과

남은 제한
- 아직 데이터가 없어 표시하지 못한 부분
- 운영자가 직접 해야 하는 API/발행/자료 등록
```

“코드를 수정했다”, “테스트가 통과했다”만으로 실제 발행 성공을 주장하면 안 된다. 실제 발행은 Actions 실행 성공, Notion URL 생성, 텔레그램 성공 상태까지 확인된 경우에만 완료라고 표현한다.

## 12. 최종 원칙

이 템플릿의 목적은 많은 정보를 보여주는 것이 아니라 아래 흐름을 매일 짧고 검증 가능하게 전달하는 것이다.

```text
무슨 일이 있었나
→ 예상 또는 전일과 무엇이 달라졌나
→ 시장은 어떻게 반응했나
→ 어떤 섹터·종목으로 전이될 수 있나
→ 무엇을 확인하면 해석이 맞거나 틀렸다고 볼 수 있나
```

디자인은 이 판단 흐름을 빠르게 읽도록 돕는 수단이다. 기능을 추가하더라도 첫 화면의 결론, 데이터 날짜, 시장 구조, 핵심 근거, 확인 조건이 흐려지면 안 된다.
